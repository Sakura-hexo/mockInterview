# 稳定性与可观测-实现（步骤 8）

对应方案：`plans/2026-11-01/稳定性与可观测-优化方案.md`。五步全部完成并真机验证。

## 变更内容

**步骤 1 角色分级与降级链**：ChatModels 增加档位参数（main 主力档 / fast 辅助档，快档未配置回退主档）；EnvKeys 新增 OPENAI_MODEL_FAST 等三键；AgentLlmCaller 按档位构造（AppConfig 装配 mainCaller 与 fastCaller、mainInvoker 与 fastInvoker 双实例：压缩/路由/简历/JD 解析走 fast，面试官与报告走 main）；AgentScopeRuntime 面试官 main 闲聊 fast，两档互挂 AgentScope 原生 fallbackModel；QueryRewriter 显式 fast。

**步骤 2 熔断与限流**：新增 MonitoredModel 装饰器包住 ChatModels 全部产出——按档位独立 CircuitBreaker（窗口 10 次最少 5 次失败率过半打开、半开等待 30 秒），打开后快速失败不等 120 秒超时；ChatStreamService 增加每用户限流（RateLimiterRegistry 按名查找，阈值随注册表配置，生产 10 轮每分钟，超限 429）；ApiException 补 tooManyRequests 工厂。

**步骤 3 业务指标**：micrometer-registry-prometheus 依赖并暴露 /actuator/prometheus；llm_call_seconds（标签 tier 与 outcome，含 ok fail rejected，在 MonitoredModel 统一记录）、interview_turn_seconds（标签 action）、sse_active Gauge、report_task_seconds 四组埋点；resilience4j 熔断器状态经 TaggedCircuitBreakerMetrics 进注册表；全部新参数为可选重载，既有单测零改动。

**步骤 4 监控栈**：compose 新增 prometheus 与 grafana 服务（profile monitoring），Prometheus 抓宿主机 8080，Grafana 预置数据源与六面板 JSON（轮时延 p50/p95、LLM 调用速率按档位、失败与熔断拒绝、熔断器状态、活跃对话轮、报告时延）。

**步骤 5 应用容器化**：backend/Dockerfile（宿主 mvn package 后 JRE21 只装 jar）；compose app 服务（profile deploy）依赖三中间件健康后启动，密钥经 env_file 注入、网络地址经 environment 覆盖；README 更新为开发期 / 监控 / 初版部署三条命令口径。

**实现中的修正**：application.yml 的 spring.data.redis 从 host/port 改为 url 并与 EnvKeys.redisUri 同源——容器内健康检查原先固定 localhost 导致整体 DOWN；限流查找改为按名不带配置（注册表为配置唯一所有者，测试可注入更紧口径）。
