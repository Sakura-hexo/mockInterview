## RD-018
题干：RDB 持久化的 save 和 bgsave 命令有什么区别？
要点：save 由主进程同步执行 RDB，期间阻塞所有客户端命令，数据集较大时服务器会长时间停止响应，生产环境基本不用。bgsave 则是 fork 一个子进程在后台生成快照，命令立即返回，主进程继续处理请求，只在 fork 瞬间有短暂阻塞，对服务可用性影响小，是生产环境执行 RDB 持久化的推荐方式。
标签：Redis,持久化
来源：个人笔记

## RD-019
题干：RDB 持久化会在哪些时机自动触发？
要点：三种场景：一是配置文件中 save 秒数 修改次数 规则满足时触发，如 save 900 1 表示 900 秒内至少 1 个键被修改就自动执行一次持久化；二是服务器收到 SHUTDOWN 正常关闭且未禁用 RDB 时，关闭前自动执行一次，保证下次启动可恢复；三是主从复制场景，从节点首次连接主节点请求数据时，主节点会在后台生成 RDB 文件发送给从节点完成全量同步。
标签：Redis,持久化
来源：个人笔记

## RD-020
题干：bgsave 的 fork 是如何借助写时复制工作的？
要点：bgsave 时主进程 fork 出子进程，父子进程共享同一份物理内存：主进程执行读操作时直接访问共享内存；一旦主进程执行写操作，操作系统会先复制被修改的内存页再写入，子进程看到的仍是 fork 瞬间的快照数据。写时复制既保证了快照数据的一致性，又避免了 fork 时复制整个数据集的开销。
标签：Redis,持久化
来源：个人笔记

## RD-021
题干：AOF 有哪几种刷盘策略？各有什么特点？
要点：appendfsync 有三个取值：always 每条写命令都立即刷盘，可靠性最高但磁盘 IO 频繁、性能最差；everysec 是默认值，命令先写入 AOF 缓冲区，每隔一秒刷一次盘，是性能与安全的折中，宕机最多丢最后一秒数据；no 完全交由操作系统决定何时把缓冲区写回磁盘，性能最好但宕机时丢失多少数据不可控。
标签：Redis,持久化
来源：个人笔记

## RD-022
题干：什么是 AOF 重写？为什么需要 AOF 重写？
要点：AOF 会记录每条写命令，而对同一个 key 的多次写操作往往只有最后一次有意义，导致文件越滚越大。AOF 重写根据当前内存中的数据生成最小命令集，用最少的命令达到与原文件相同的恢复效果，大幅缩减文件体积、加快恢复速度。可通过 bgrewriteaof 命令触发，重写同样由子进程在后台完成，不阻塞主进程。
标签：Redis,持久化
来源：个人笔记

## RD-023
题干：Redis 重启时是如何恢复数据的？
要点：恢复操作很简单：把 RDB 或 AOF 文件放到 Redis 的数据目录下，启动 redis-server 即可，用 AOF 恢复需在配置中开启 AOF。加载有优先级：AOF 开启且文件存在时优先加载 AOF，因为它保存的数据集通常比 RDB 更完整；AOF 未开启或文件不存在时才加载 RDB。文件加载成功则启动成功，文件存在错误则启动失败并打印错误信息。
标签：Redis,持久化
来源：个人笔记

## RD-024
题干：说一下布隆过滤器的原理？为什么会误判？
要点：布隆过滤器由长度为 m 的位数组和 k 个哈希函数组成，初始所有位为 0。添加元素时用 k 个哈希函数计算出 k 个位置并置 1；查询时同样计算，任一位置为 0 则元素一定不存在，全为 1 则可能存在。不同元素的哈希位置可能重叠，因此存在误判，且位数组越小误判率越高，越大越准但更耗内存。它空间占用极小、查询极快，常放在缓存前拦截不存在的数据。
标签：Redis,缓存
来源：个人笔记

## RD-025
题干：如何发现 Redis 中的热 key？
要点：三条途径：一是客户端统计，命令都从客户端发出，可用全局字典记录每个 key 的调用次数，离 key 最近且开销小；二是代理端统计，Twemproxy、Codis 这类代理架构下所有请求都经过代理，可在代理层汇总监控；三是服务端统计，用 monitor 命令监听 Redis 执行的所有命令来找出热点，但 monitor 本身有性能开销，使用需谨慎。
标签：Redis,缓存
来源：个人笔记

## RD-026
题干：发现热 key 之后该如何处理？
要点：核心思路是避免所有访问压到单个实例上：一是打散热 key，给 key 加上前缀或后缀，把请求分摊到不同的 Redis 节点；二是引入二级缓存，把热 key 的值加载到应用本地内存（如 JVM）中，后续请求直接读本地，不再打到 Redis。同时可对热 key 不设过期时间，避免失效瞬间大量线程集中重建缓存压垮后端。
标签：Redis,缓存
来源：个人笔记

## RD-027
题干：什么是缓存预热？
要点：缓存预热指系统启动或上线前，提前把预定义的热点数据加载到缓存中，避免运行初期大量请求因缓存未命中直接打到数据库，导致响应缓慢甚至压垮数据库。通过预热，系统上线后能立即以较高缓存命中率的状态提供服务，显著降低首次访问的延迟，实践中常配合定时刷新来保持缓存数据的新鲜度。
标签：Redis,缓存
来源：个人笔记

## RD-028
题干：说一下 Redis 事务的原理？
要点：MULTI 开启事务后，后续命令不会立即执行而是依次入队；EXEC 触发时队列中的命令被一次性顺序执行；执行前可用 DISCARD 清空队列放弃事务。WATCH 用于实现乐观锁：被监视的 key 若在 EXEC 执行前被其他客户端修改，整个事务会被取消并返回错误。注意 Redis 事务不支持回滚，队列中某条命令运行时出错，其余命令仍会继续执行。
标签：Redis,事务
来源：个人笔记

## RD-029
题干：Redis 主从架构下的分布式锁有什么问题？了解 RedLock 吗？
要点：主从复制是异步的：主节点加锁成功但尚未同步给从节点时就宕机，从节点晋升为新主后锁就丢了，其他线程可以再次加锁，造成并发冲突。RedLock 的思路是不依赖单一实例：向多个相互独立的 Redis 实例依次加锁，超过半数实例加锁成功才算持锁。但该方案部署复杂、性能差，实践中一般不推荐使用。
标签：Redis,分布式锁
来源：个人笔记

## RD-030
题干：Redis 和 Zookeeper 实现分布式锁有什么区别？
要点：设计思想不同：Redis 是 AP 思想，主从异步复制，追求性能与可用性，加解锁速度快，但极端情况下锁可能因主从切换而丢失；Zookeeper 是 CP 思想，写请求需集群过半节点确认，主节点宕机后锁数据不会丢，能保证强一致，但性能低于 Redis。选型上，性能优先且可容忍小概率失锁用 Redis，正确性要求严格则用 Zookeeper。
标签：Redis,分布式锁
来源：个人笔记

## RD-031
题干：哨兵是通过哪些定时任务来监控节点的？
要点：三个定时任务：每隔 10 秒，每个哨兵节点向主节点和从节点发送 info 命令，获取最新的主从拓扑结构；每隔 2 秒，每个哨兵节点向 _sentinel_:hello 频道发布自己对主节点的判断以及自身信息，供哨兵之间交换认知；每隔 1 秒，每个哨兵节点向主节点、从节点及其他哨兵发送 ping 命令做心跳检测，判断对方是否可达。
标签：Redis,哨兵
来源：个人笔记

## RD-032
题干：什么是主观下线和客观下线？
要点：主观下线：哨兵每隔 1 秒对主节点、从节点和其他哨兵做 ping 心跳检测，若某节点超过 down-after-milliseconds 设置的时间仍未有效回复，该哨兵就单方面判定其下线。客观下线：若被判定的是主节点，该哨兵会询问其他哨兵对主节点的判断，同意的哨兵数达到 quorum 个时，才确认主节点真正故障并进入故障转移。主观下线可能是单个哨兵网络抖动导致的误判，客观下线用多数意见来兜底。
标签：Redis,哨兵
来源：个人笔记

## RD-033
题干：哨兵之间是如何选出领导者的？
要点：基于 Raft 算法思想：每个在线哨兵都有资格成为领导者，确认主节点主观下线后，它会向其他哨兵发送请求，要求将自己设置为领导者；收到请求的哨兵遵循先到先得，若尚未投过票就同意该请求，否则拒绝。当某哨兵的得票数达到 max(quorum, 哨兵总数/2+1) 时成为领导者，负责执行故障转移；若一轮选举无人达标，则进入下一轮选举。
标签：Redis,哨兵
来源：个人笔记

## RD-034
题干：哨兵执行故障转移时，新主节点是怎么选出来的？
要点：先过滤不健康的从节点：已断线、5 秒内没有回复过哨兵 ping、与主节点失联时间超过 down-after-milliseconds 十倍的都会被排除。然后在剩余从节点中依次按三个条件挑选：选 slave-priority 从节点优先级最高的；不存在则选复制偏移量最大即数据最完整的；仍不存在则选 runid 最小的。选出的从节点升级为新主，其他从节点改为复制新主，故障实例恢复后也以新主为主。
标签：Redis,哨兵
来源：个人笔记

## RD-035
题干：什么是哨兵架构下的脑裂问题？
要点：脑裂指主节点与哨兵、从节点之间发生网络分区：哨兵因联系不上主节点而发起故障转移选出新主，但旧主实际还活着并继续接收客户端写入。分区恢复后，旧主被降级为从节点，会清空自身数据并从新主重新同步，分区期间写入旧主的数据就丢失了。缓解思路是限制主节点的可写条件，比如从节点数量不足或延迟过高时拒绝写入，减少分区期间的写入量。
标签：Redis,哨兵
来源：个人笔记

## RD-036
题干：有了主从和哨兵，为什么还需要分片集群？
要点：主从加哨兵解决的是高可用问题，数据仍然全量存放在单个主节点上。当数据量大到单机内存存不下，或写并发高到单个主节点扛不住时，就需要分片集群：数据按规则拆分到多个主节点，每个节点只存一部分数据、各自承担一部分写压力；而从节点只能扩展读能力，无法分担写。分片集群同时解决海量数据存储和高并发写两个问题。
标签：Redis,集群
来源：个人笔记

## RD-037
题干：说一下 Redis 分片集群的哈希槽机制？
要点：Redis Cluster 共有 16384 个哈希槽，槽是数据管理与迁移的基本单位。读写 key 时先对 key 做 CRC16 哈希再对 16384 取模，得到所属槽，再定位到负责该槽的节点。每个节点负责一段槽区间，扩容缩容时只需把部分槽连同槽中数据迁移到新节点，其余数据位置不变，过程平滑且分布均匀。槽数是 2 的 14 次方，与 HashMap 数组长度取 2 的幂有异曲同工之妙，能减少扩容时的数据迁移量。
标签：Redis,集群
来源：个人笔记

## RD-038
题干：Redis 分片集群是如何搭建起来的？
要点：三步：一是设置节点，每个节点开启 cluster-enabled yes 以集群模式运行，要组成完整的高可用集群一般至少需要 6 个节点；二是节点握手，通过客户端执行 cluster meet 命令，让各节点基于 Gossip 协议彼此感知，一个个独立节点就此组成多节点集群；三是分配槽，用 cluster addslots 命令把 16384 个槽分给各主节点，节点只有分配到槽，才能响应与这些槽关联的键命令。
标签：Redis,集群
来源：个人笔记

## RD-039
题干：分片集群中节点的故障是如何被发现的？
要点：集群内节点通过 Gossip 协议的 ping 和 pong 消息通信，每个节点都会定期向其他节点发送 ping 消息，接收方回复 pong 作为响应。若在 cluster-node-timeout 时间内与某节点的通信一直失败，发起节点就把它标记为主观下线状态；该判断会随 Gossip 消息在集群内传播，当半数以上持有槽的主节点都标记某节点主观下线时，触发客观下线流程，进入故障转移。
标签：Redis,集群
来源：个人笔记

## RD-040
题干：分片集群的故障转移流程是怎样的？
要点：被客观下线的节点若是持有槽的主节点，需要从它的从节点中选出一个替换：先做资格检查，剔除与主节点断线时间过长等不具备资格的从节点；符合条件的从节点在到达预设的故障选举时间后发起选举；持有槽的主节点处理选举消息并投票，每个配置纪元内只能投给一个从节点，获得超过半数选票即 N/2+1 张的从节点胜出，保证选出唯一节点；最后它执行替换操作，升级为新的主节点接管槽。
标签：Redis,集群
来源：个人笔记

## MY-017
题干：说一下 MySQL 中一条查询语句的执行流程？
要点：客户端发送 SQL 后，连接器先建立连接并校验权限；解析器做词法与语法分析，校验表和列是否存在；优化器确定执行计划，包括选用索引和表连接顺序；执行器调用存储引擎 API 读写数据并返回结果。查询缓存在 MySQL 8.0 中已移除；存储引擎是插件式的，如 InnoDB 支持事务而 MyISAM 不支持。
标签：MySQL,基础
来源：个人笔记

## MY-018
题干：说一下 InnoDB 和 MyISAM 的区别？
要点：InnoDB 是 MySQL 5.5 之后的默认引擎，支持事务、行级锁和外键，必须有主键，索引为聚簇结构，行级锁让并发写入性能更高；MyISAM 不支持事务和外键，只支持表级锁，索引为非聚簇结构，适合读多写少的场景。此外还有 Memory 引擎，数据放在内存中，适合做临时表和数据量小的场景。
标签：MySQL,存储引擎
来源：个人笔记

## MY-019
题干：说一下 MySQL 有哪些常见的日志文件？
要点：服务器层有四种：错误日志记录启动、运行、停止时的问题；慢查询日志记录超过 long_query_time 的 SQL，用于定位和优化慢 SQL；通用查询日志记录所有连接和语句；binlog 记录所有修改数据的操作，用于备份恢复和主从复制。InnoDB 引擎层有两种：redo log 记录物理页修改，用于崩溃恢复；undo log 记录修改前的旧值，用于回滚和 MVCC。
标签：MySQL,日志
来源：个人笔记

## MY-020
题干：说一下 binlog 和 redo log 有什么区别？
要点：所属层次不同，binlog 是服务器层日志，所有存储引擎共用；redo log 是 InnoDB 特有的。记录内容不同，binlog 是逻辑日志，记录事务的具体操作内容；redo log 是物理日志，记录数据页的修改。写入方式不同，binlog 在事务提交时追加写入，不覆盖旧文件；redo log 在事务执行中持续写入，循环使用，写满要擦除。
标签：MySQL,日志
来源：个人笔记

## MY-021
题干：为什么 redo log 和 binlog 要采用两阶段提交？
要点：两个日志相互独立，分开写会不一致。先写 redo log 后写 binlog，崩溃后主库恢复了更新，但 binlog 缺这条记录，从库和备份会少这次修改；先写 binlog 后写 redo log，崩溃后主库并未真正更新，从库却多出这次修改。两阶段提交先写 redo log 并置为 prepare，binlog 落盘成功后再 commit，保证两边一致。
标签：MySQL,日志
来源：个人笔记

## MY-022
题干：说一下 redo log 的工作原理，什么时候刷入磁盘？
要点：InnoDB 采用先写日志（WAL）机制：修改数据时先写 redo log，再异步刷回数据文件，崩溃后重放日志即可保证持久性。redo log 先写入内存中的 log buffer，在这些时机会刷盘：日志量约占缓冲区一半、事务提交、后台线程约每秒刷新一次、正常关闭服务器以及触发 checkpoint。日志以 512 字节块循环写入，write pos 追上 checkpoint 时需推进 checkpoint 腾出空间。
标签：MySQL,日志
来源：个人笔记

## MY-023
题干：为什么加了索引查询会变快？
要点：数据存放在磁盘上，没有索引时只能全表扫描，逐行读取并判断匹配，时间复杂度 O(n)，数据量大时磁盘 IO 非常多。索引把列值按序组织成 B+ 树，从根节点逐层向下定位，时间复杂度降到 O(logN)，少量 IO 即可找到记录位置；而且索引文件比数据文件小得多，加载和遍历的成本都更低。
标签：MySQL,索引
来源：个人笔记

## MY-024
题干：什么是 InnoDB 的自适应哈希索引？
要点：哈希索引等值查询快，但不支持范围查询，所以 InnoDB 不提供手动创建哈希索引的选项，只使用 B+ 树。自适应哈希索引是引擎自动维护的：当 InnoDB 监测到某些索引页被频繁访问时，会在缓冲池中为这些热页自动建立哈希索引，加速等值定位，全程无需人工干预。它解决的是热点页的等值查询提速问题。
标签：MySQL,索引
来源：个人笔记

## MY-025
题干：设计索引时有哪些注意事项？

## MY-026

## NET-025
题干：说一下 TCP 四次挥手后为什么要等待 2MSL 才进入 CLOSED？

## JU-027
题干：说一下并发编程的原子性、可见性、有序性分别指什么？如何保证？
要点：原子性指操作不可被中断分割，JMM 只保证基本变量的读写原子性，更大代码块用 synchronized 或 Lock 保证；可见性指一个线程的修改能立即被其他线程看到，主要靠 volatile，final 和 synchronized 也能保证；有序性指程序按代码顺序执行，因为存在指令重排，需用 volatile 禁止重排，或用 synchronized 保证临界区内串行执行。
标签：并发,JMM
来源：个人笔记

## JU-028
题干：什么是指令重排？happens-before 和 as-if-serial 是什么意思？
要点：编译器和处理器为了提高性能会重排指令。as-if-serial 语义保证单线程程序无论怎么重排，执行结果都不变，存在数据依赖的操作不会被重排。happens-before 是 JMM 对程序员的承诺：若 A happens-before B，则 A 的结果对 B 可见且排在 B 之前；只要结果不变，底层允许不按该顺序执行。双重检查单例中 new 的重排就靠 volatile 防止。
标签：并发,JMM
来源：个人笔记

## JU-029
题干：为什么要使用线程池？适合什么场景？
要点：一是降低资源消耗，线程复用避免频繁创建销毁的开销；二是提高响应速度，请求到来直接取用空闲线程；三是统一管理线程，可控并发、便于调优监控。场景分两类：实时请求需要快速响应，可预先备好线程；批量任务不必立即响应，用队列缓冲并控制核心线程数，避免线程过多造成频繁上下文切换。
标签：并发,线程池
来源：个人笔记

## JU-030
题干：说一下线程池有哪几种状态？是如何切换的？
要点：线程池有五种状态：RUNNING，可接收新任务并处理队列任务；调用 shutdown() 进入 SHUTDOWN，不再接收新任务但会处理完存量任务；调用 shutdownNow() 进入 STOP，不接新任务并中断执行中的任务；任务和线程都清空后进入 TIDYING，执行完 terminated 钩子方法后变为 TERMINATED。状态只能单向切换，终止后的线程池不能复用。
标签：并发,线程池
来源：个人笔记

## JU-031
题干：说一下 synchronized 的锁升级过程？JDK 1.6 对锁做了哪些优化？
要点：锁只升不降：无锁、偏向锁、轻量级锁、重量级锁逐级膨胀。首次获锁把线程 ID 写进对象头 Mark Word 就是偏向锁，同线程再进入几乎无开销；有竞争就撤销偏向升级轻量级锁，用 CAS 将 Mark Word 换成指向栈中锁记录的指针；自旋失败或竞争激烈则膨胀为依赖操作系统互斥量的重量级锁。其他优化有自适应自旋、锁粗化、锁消除。

## JU-032
题干：说一下 ThreadLocal 的底层实现原理？
要点：每个 Thread 内部持有一个 ThreadLocalMap，它虽叫 Map 但未实现 Map 接口：底层是 Entry 数组，Entry 以 ThreadLocal 的弱引用为 key、以变量副本为 value。定位下标用 threadLocalHashCode 与数组长度减一做与运算，相当于哈希取余；发生冲突时用开放定址法线性探测，而不是 HashMap 的链地址法。

## JU-033
题干：父子线程之间如何共享 ThreadLocal 的数据？
要点：用 InheritableThreadLocal。Thread 类中除了 threadLocals，还有 inheritableThreadLocals 变量；创建子线程时 init 方法发现父线程的 inheritableThreadLocals 不为空，就把它复制给子线程，因此主线程设置的值子线程能直接读到。局限是复制只在创建线程时发生一次，线程池复用线程时拿不到最新值，需要 TransmittableThreadLocal 等方案弥补。

## JB-018
题干：说一下 JVM、JRE 和 JDK 的区别？

## JB-019

## JB-020
题干：说一下抽象类和接口的区别？各自适合什么场景？
要点：单继承多实现：一个类只能继承一个抽象类，却能实现多个接口，比如定义线程类推荐实现 Runnable，把继承名额留出来。语义上抽象类是 is-a，为一组相关类提供公共骨架，可以有状态和构造方法；接口是 has-a，定义行为标准，如实现 Serializable 即具备可序列化能力。选型上，公共基础框架用抽象类，跨类别的统一行为用接口。

## JB-021
题干：说一下 throw 和 throws 的区别？
要点：throw 用在方法体内，手动抛出一个具体的异常对象，执行到这行方法立即结束；throws 用在方法签名上，声明该方法可能抛出的异常类型，把处理责任交给调用者，调用者要么 try-catch 捕获，要么继续向上声明抛出。配合起来：编译时异常必须被显式处理，运行时异常如空指针则不强制。try-catch-finally 是捕获处理的基本结构。

## JB-022
题干：说一下 Java 中 IO 流的分类？
要点：按流向分输入流和输出流；按数据单位分字节流和字符流，字节流以字节为单位处理音频、图像等二进制数据，字符流面向文本数据；按功能分节点流和处理流，节点流直接连接数据源，处理流包装已有流提供缓冲、转换等增强能力，是典型的装饰者模式应用。顶层抽象：字节流 InputStream/OutputStream，字符流 Reader/Writer。

## JB-023
题干：说一下 BIO、NIO、AIO 的区别？
要点：BIO 阻塞模型：线程执行 IO 时被阻塞，每个连接独占一个线程，适合连接数少的场景。NIO 非阻塞模型：通过 Selector 监控多个 Channel 的事件，一个线程可服务大量连接，适合连接多但单次处理短的场景。AIO 异步模型：发起请求立即返回，完成后回调通知，适合连接多且持续时间长的场景。
标签：Java基础,IO
来源：个人笔记

## JB-024
题干：说一下 NIO 的三大核心组件？
要点：Channel 通道：类似流但双向，可同时读和写，是数据传输的通道。Buffer 缓冲区：读写数据都要先经过它，本质是可操作的内存块，用 flip、clear 等方法切换读写模式。Selector 选择器：多路复用核心，一个线程可监听多个 Channel 的就绪事件再分发处理，避免每个连接建一个线程，是 NIO 支撑高并发的关键。
标签：Java基础,IO
来源：个人笔记

## JB-025
题干：说一下 Java 8 的 Stream 流？
要点：Stream 提供对集合的声明式处理，操作分两类：中间操作如 filter、map、sorted，返回新的 Stream 支持链式调用，且是惰性的，单独存在不会执行任何计算；终端操作如 collect、forEach、reduce，触发整条流水线真正执行并产出结果。一条流可以有多个中间操作但只能有一个终端操作，流消费一次后就失效，不能重复使用。

## JV-007
题干：说一下分代回收的堆划分和对象流转？
要点：堆按 1:2 分新生代与老年代，新生代内部 Eden 与两个 Survivor 按 8:1:1。新对象优先分配 Eden，Minor GC 后存活对象在两个 Survivor 间往复并累加年龄，默认十五岁晋升老年代；大对象直接进老年代避免反复复制。老年代放不下或担保失败触发 Full GC。
标签：JVM,垃圾回收
来源：个人笔记

## JV-008
题干：JVM 如何判断一个对象是不是垃圾？
要点：两种思路。引用计数法在对象头维护被引用次数，实现简单但无法解决循环引用。HotSpot 采用可达性分析：从 GC Roots 等起点沿引用链向下搜索，当从 GC Roots 到某对象之间没有任何引用相连时即为不可达，判定可以回收，相互引用但整体不可达的循环引用对象也能被正确识别。
标签：JVM,垃圾回收
来源：个人笔记

## JV-009
题干：哪些引用可以作为 GC Roots？
要点：GC Roots 不是对象，是一组必须活跃的引用，是程序运行时一切引用链的源头。主要包括：虚拟机栈中的引用（方法参数、局部变量等）、本地方法栈中 JNI 的引用、类的静态变量、运行时常量池中的常量（String 或 Class 类型）。
标签：JVM,垃圾回收
来源：个人笔记

## JV-010
题干：对象在什么情况下会进入老年代？
要点：长期存活的对象每熬过一次 Minor GC 年龄加一，达到阈值（默认 15，可用 -XX:MaxTenuringThreshold 调整）就晋升老年代；大对象超过 -XX:PretenureSizeThreshold 直接进老年代，避免在 Survivor 间反复复制；动态年龄判定：Survivor 中同龄对象总大小超过空间一半时，不小于该年龄的对象直接晋升；此外 Survivor 放不下时也会提前晋升。
标签：JVM,垃圾回收
来源：个人笔记

## JV-011
题干：说一下 Minor GC 和 Full GC 分别在什么情况下触发？
要点：Eden 区空间不足以分配新对象时触发 Minor GC。Full GC 的触发场景更多：Young GC 前检查发现老年代可用连续空间小于历次晋升对象的平均大小；Young GC 后晋升对象老年代放不下；老年代使用率达到阈值；空间分配担保失败，即 To 区放不下或对象年龄到期要晋升而老年代装不下；永久代实现的方法区空间不足；System.gc() 等命令显式触发。
标签：JVM,垃圾回收
来源：个人笔记

## JV-012
题干：说一下一个对象从创建到回收的完整过程？
要点：new 时先检查常量池能否定位到类的符号引用、类是否已加载解析初始化，没有则先执行类加载；接着为新对象分配内存；分配后把内存空间初始化为零值（数值为 0、布尔为 false、引用为 null）；再设置对象头，记录所属类、哈希码、GC 分代年龄；最后执行构造方法赋值。对象不再被任何引用指向后成为垃圾，经可达性分析判定不可达即被收集器回收。
标签：JVM,内存管理
来源：个人笔记

## JV-013
题干：说一下强引用、软引用、弱引用和虚引用的区别？
要点：强引用只要从 GC Roots 可达就永不回收。软引用描述有用但非必需的对象，内存溢出前会被列入二次回收范围，仍不够才抛 OOM，常用于缓存。弱引用只要发生 GC 就被回收。虚引用无法取得对象，必须配合引用队列，对象被回收时虚引用入队，由 Reference Handler 线程处理并释放直接内存等资源。
标签：JVM,垃圾回收
来源：个人笔记

## JV-014
题干：什么是逃逸分析？它有什么好处？
要点：逃逸分析是分析对象动态作用范围的技术：对象被传到外部方法叫方法逃逸，可能被其他线程访问叫线程逃逸。基于分析结果可做三类优化：栈上分配，不逃逸的对象随栈帧出栈销毁，减轻 GC 压力；同步消除，不会逃出线程的对象其同步措施可安全去掉；标量替换，把对象拆成基本类型成员变量直接在栈上读写，甚至不必创建对象。
标签：JVM,内存管理
来源：个人笔记

## JV-015
题干：常见的垃圾收集器有哪些？如何选择？
要点：按演进分三类：Serial 单线程收集，STW，适合小内存（约百兆级）或单线程环境；Parallel 多线程并行，吞吐量优先，适合可接受秒级停顿、追求峰值性能的场景；CMS 与 G1 并发收集、低停顿，适合响应时间敏感的服务，其中 G1 面向大内存且停顿可预测；ZGC 适合响应时间优先或堆很大的场景。选择时在吞吐量与停顿时间之间权衡。
标签：JVM,垃圾回收
来源：个人笔记

## JV-016
题干：说一下类加载的完整过程？
要点：加载：查找并读取 Class 文件，在内存中生成 Class 对象；验证：保证被加载类的准确性与合法性；准备：为类变量分配内存并设置零值；解析：把常量池的符号引用转换为直接引用；初始化：执行静态变量赋值和静态代码块。之后 JVM 从入口方法开始执行程序，程序执行完后销毁 Class 对象，完成卸载。

## JV-017
题干：JDK 8 为什么用元空间替换永久代？
要点：JDK 7 的永久代在堆内，存放类信息、静态变量、常量和编译后代码，大小受堆限制，加载类过多时容易内存溢出。JDK 8 移除永久代，把这些数据放到本地内存的元空间中，默认只受可用本地内存约束，大大降低被打满的风险；同时字符串常量池早已移入堆中，也减轻了这块的负担。
标签：JVM,内存结构
来源：个人笔记

## JV-018
题干：什么是直接内存？它和堆内存有什么区别？
要点：直接内存不属于 JVM 运行时数据区，不由 JVM 管理，是向操作系统申请的本地内存。常见于 NIO 操作，用作数据缓冲区，避免数据在 JVM 堆与系统之间的来回复制，读写性能高；但分配和回收成本较高，也不受 JVM 堆大小限制和垃圾回收直接管理，配置不当同样可能内存溢出。
标签：JVM,内存结构
来源：个人笔记

## JV-019
题干：说一下内存溢出和内存泄漏的区别？哪些写法容易造成内存泄漏？
要点：内存溢出是分配内存时空间不足，抛 OutOfMemoryError；内存泄漏是不再使用的对象因被引用持有而无法回收，可用内存持续减少，累积后引发溢出。常见泄漏写法：静态集合持有对象、单例持有外部引用、连接和 IO 流用完不 close、变量作用域过大、HashMap 中 key 的 hash 值被改导致无法删除、ThreadLocal 用完不 remove。
标签：JVM,内存管理
来源：个人笔记

## JV-020
题干：线上频繁 Minor GC 或 Full GC，该怎么排查和优化？
要点：频繁 Minor GC 多因新生代过小、Eden 很快被填满，可增大 -Xmn 降低频率。频繁 Full GC 先列可能原因：大对象、内存泄漏、长生命周期对象进老年代、代码显式调用 gc、参数设置不当；再用 jstat -gcutil 观察 GC 频率，jmap -histo 看对象数量排序，dump 后用 MAT 或 VisualVM 分析，定位可疑对象并结合晋升条件找到代码修复。

## JV-021

## JV-022
题干：线上服务 CPU 飙高，怎么排查？

## JB-033
题干：说一下 ArrayList 的扩容机制？
要点：ArrayList 底层是数组，添加元素时如果元素个数加一超过数组长度就触发扩容：创建一个 1.5 倍容量的新数组（新容量等于旧容量加上旧容量右移一位），把原数组元素整体拷贝过去，引用再指向新数组。因此容量不足时的连续添加有拷贝开销，能预估数据量时建议初始化指定容量，减少扩容次数。
标签：Java集合,List
来源：个人笔记

## JB-034
题干：ArrayList 是线程不安全的，怎么解决？
要点：两种方案：一是用 Collections.synchronizedList 包装，内部通过 synchronized 对象锁保证线程安全；二是直接用 CopyOnWriteArrayList，采用读写分离：读操作无锁可并发读，写操作先复制一份新数组，在新副本上修改，完成后把原引用指向新数组。写时复制代价高，适合读多写少场景，且迭代不需要加锁，不会抛并发修改异常。
标签：Java集合,List
来源：个人笔记

## JB-035
题干：说一下 HashSet 和 TreeSet 的实现原理？
要点：HashSet 底层基于 HashMap 实现，元素作为 key 存储，value 统一用一个固定的占位对象，借助 key 不可重复的特性完成去重，add 时返回 false 即已存在。TreeSet 底层基于 TreeMap，用红黑树维护元素顺序，靠比较结果为 0 来判定元素重复。两者都线程不安全。
标签：Java集合,Set

## JB-036
题干：说一下 PriorityQueue 的底层实现？
要点：优先级队列是基于二叉堆的无界队列，默认维护小顶堆，元素按自然顺序或传入的 Comparator 排序，队头始终是最小元素。入队出队通过上浮、下沉调整堆结构，时间复杂度为 O(logn)，适合任务调度、Top K 等频繁取最值的场景。它线程不安全，多线程场景应使用阻塞式的 PriorityBlockingQueue。
标签：Java集合,Queue
来源：个人笔记

## JB-037
题干：说一下 HashMap 的 put 流程？
要点：先计算 key 的哈希值（hashCode 高低位异或做扰动）；首次 put 先初始化数组；再按哈希定位桶下标，桶为空直接放入；不为空则判断 key，相同就覆盖 value；是树节点就插入红黑树，否则尾插到链表，链表长度达到 8 且数组足够长时转为红黑树；最后判断元素总数超过阈值则扩容。get 类似：算哈希定位桶，先匹配首节点，再查红黑树或遍历链表。
标签：Java集合,Map
来源：个人笔记

## JB-038
题干：HashMap 为什么把负载因子定为 0.75？什么时候扩容？
要点：元素数量超过数组容量乘 0.75 的阈值就触发扩容，容量翻倍。0.75 是空间与时间的折中：设得偏大，桶的空位比较少时才扩容，哈希冲突概率上升，查询变慢；设得偏小，冲突少但很快就要扩容，空间成本增加。另外 JDK 8 扩容迁移时，元素新位置要么在原下标，要么等于原下标加旧容量，无需重新计算。
标签：Java集合,Map
来源：个人笔记

## JB-039
题干：为什么 HashMap 用红黑树，而不是二叉搜索树或 AVL 树？
要点：链表过长时查找退化到 O(n)，树化后可降到 O(logn)。二叉搜索树在极端插入顺序下会退化成链表；AVL 树严格平衡，查询快但插入删除时可能频繁旋转，维护成本高。红黑树是折中方案：不追求严格平衡，插入删除只需少量旋转加变色调整，兼顾查询效率与修改成本，靠左旋右旋和染色维持黑高一致。
标签：Java集合,Map
来源：个人笔记

## JB-040
题干：HashMap 是线程安全的吗？多线程使用会有什么问题？
要点：不安全。典型问题：JDK 7 头插法在并发扩容时可能形成环形链表导致死循环，JDK 8 改为尾插修复；并发 put 时计算出相同位置会互相覆盖，导致元素丢失；一个线程 put 触发扩容时，另一线程 get 可能返回 null。替代方案：Hashtable 方法级 synchronized 性能差；Collections.synchronizedMap 包装加对象锁；推荐 ConcurrentHashMap。
标签：Java集合,Map
来源：个人笔记

## JB-041
题干：LinkedHashMap 是怎么保证有序的？
要点：LinkedHashMap 在 HashMap 基础上维护了一条双向链表，节点 Entry 除了继承 HashMap 的 Node 属性外，增加了 before 和 after 指针标识前驱后继，并维护头尾节点，遍历时按链表顺序输出。支持插入顺序和访问顺序两种模式，访问顺序模式下最近访问的节点会移到链表尾部，是手写 LRU 缓存的经典基础。
标签：Java集合,Map
来源：个人笔记

## JB-042
题干：TreeMap 是怎么实现有序的？和 HashMap 怎么选型？
要点：TreeMap 底层是红黑树，key 必须实现 Comparable 或构造时传入 Comparator，按比较结果决定元素在左右子树的位置，插入删除时通过旋转和着色保持平衡，查找效率 O(logn)。HashMap 基于哈希表，无冲突时查找近似 O(1) 但不保证顺序。需要有序遍历、范围查询或自定义排序规则选 TreeMap，单纯按 key 存取选 HashMap。
标签：Java集合,Map
来源：个人笔记

## JB-043
题干：HashMap 内部是怎么判断两个 Key 相同的？
要点：先用 key 的 hashCode 计算哈希码并定位桶，哈希码相同不代表 key 相同，只是第一轮筛选。在桶内逐个比较：先用 == 判断两个引用是否指向同一对象，同一对象则 hashCode 和 equals 必然都通过，可快速确认；否则再用 equals 精确比较，只有 equals 也返回 true，两个 key 才被视为相同并执行覆盖。
标签：Java集合,Map
来源：个人笔记

## OS-009
题干：说一下并发和并行的区别？
要点：并发指一段时间内多个任务都会被处理，但某一时刻只有一个任务在执行，单核 CPU 靠时间片轮转快速切换进程，宏观上表现为同时运行。并行指同一时刻多个任务真正同时执行，需要多核处理器支持，不同程序放在不同核心上物理地同时运行。一句话概括：并发是宏观同时、微观交替，并行是微观也同时。
标签：操作系统,进程
来源：个人笔记

## OS-010
题干：什么是上下文切换？线程的上下文切换和进程有什么不同？
要点：上下文切换是 CPU 从一个任务切到另一个任务的过程：先保存当前任务的寄存器、程序状态等上下文，调度器选出下一个任务，再恢复其上下文继续执行。进程切换要切换整个地址空间和资源，代价高；同进程的两个线程共享虚拟内存，切换时地址空间不动，只需切换线程私有的栈、寄存器等数据，因此更轻量。
标签：操作系统,进程
来源：个人笔记

## OS-011
题干：什么是僵尸进程和孤儿进程？分别有什么危害？
要点：僵尸进程是子进程已退出，但父进程没有调用 wait 或 waitpid 回收，其进程描述符仍留在进程表中，大量堆积会耗尽系统资源。孤儿进程是父进程先退出而子进程仍在运行，它们会被 init 进程收养并由其完成状态收集，因此本身没有危害。核心区别：僵尸是子进程死了没人回收，孤儿是父进程死了子进程还活着。
标签：操作系统,进程
来源：个人笔记

## OS-012
题干：说一下线程有哪些实现方式？
要点：分三种。内核态线程在内核空间由内核直接管理调度，单个线程阻塞不影响其他线程，但切换要陷入内核、开销大；用户态线程在用户空间实现，内核无感知，切换开销小，但一个线程阻塞会导致整个进程阻塞；混合实现是现代操作系统的做法，内核态线程数量少、用户态线程数量多，多个用户态线程映射到内核线程上，兼顾效率与调度能力。
标签：操作系统,线程
来源：个人笔记

## OS-013
题干：说说互斥锁和信号量是如何实现线程同步的？
要点：互斥锁保护临界区，同一时刻只允许一个线程进入，抢不到锁的线程主动让出 CPU 进入阻塞，避免忙等浪费资源。信号量用整型变量表示资源数量，配合两个原子操作：P 操作在值大于 0 时减 1 进入临界区，否则阻塞等待；V 操作将值加 1 并唤醒阻塞线程。信号量初值为 1 时效果近似互斥锁，大于 1 时可控制多个线程同时访问。
标签：操作系统,线程同步
来源：个人笔记

## OS-014
题干：什么是活锁和饥饿？它们和死锁有什么区别？
要点：活锁指线程没有阻塞、状态一直在变化，但整组线程始终无法推进，就像两人过窄桥互相礼让却总让向同一边。饥饿指某个线程一直得不到所需资源而无法向前执行，其他线程仍可正常运行。与死锁的区别：死锁中的线程全部阻塞等待、完全不动；活锁中的线程在忙却没有进展；饥饿只是个别线程被饿着，系统整体还在运转。
标签：操作系统,线程
来源：个人笔记

## OS-015
题干：说一下软链接和硬链接的区别？
要点：硬链接是在目录下新建一个条目，记录文件名并指向源文件的 inode，与源文件地位平等，删除任意一个条目，只要引用数不为 0 文件就仍存在；限制是不能跨文件系统、不能链接目录。软链接是独立的新文件，有自己的 inode，内容是目标文件的路径，访问时跳转到目标文件；可以跨文件系统，目标被删除后链接仍在但会失效。
标签：操作系统,文件系统
来源：个人笔记

## OS-016
题干：说一下阻塞 IO 和非阻塞 IO 的区别？
要点：阻塞 IO 是线程调用 read 后一直等待，直到内核数据准备好且从内核缓冲区拷贝到用户缓冲区才返回，期间线程做不了别的事。非阻塞 IO 是数据未准备好时 read 立即返回，线程可以去处理其他逻辑，但需不断轮询内核直到数据就绪、拷贝完成。两者都涉及两个阶段：等待内核数据准备、数据从内核态拷贝到用户态。
标签：操作系统,IO
来源：个人笔记

## OS-017
题干：说一下 select、poll、epoll 的区别？
要点：select 用位图保存关注的描述符，每次调用都要在用户态和内核态间整体拷贝集合并线性遍历，描述符个数默认上限 1024；poll 改用动态数组突破了数量限制，但拷贝和 O(n) 遍历的问题依旧；epoll 在内核用红黑树管理描述符、只需注册一次，就绪事件经回调进入就绪链表，调用 epoll_wait 只返回活跃的描述符，适合海量并发连接。
标签：操作系统,IO
来源：个人笔记

## OS-018
题干：为什么需要多级页表？它是怎么减少内存开销的？
要点：单级页表必须为整个虚拟地址空间建立连续的页表，即使大部分地址空间没被程序使用，页表也得全量占用内存。多级页表把页表本身再分页，按需只为实际用到的地址区域分配下级页表，未使用的区域不建页表，页表占用的内存大幅减少；代价是地址转换要多次访问内存，所以实际会配合 TLB 缓存页表项来加速。
标签：操作系统,内存管理
来源：个人笔记

## OS-019
题干：什么是快表 TLB？它解决了什么问题？
要点：程序具有局部性，一段时间内只会访问少数几个内存区域，对应的页表项非常集中。快表 TLB 就是 CPU 芯片内专门缓存最常访问页表项的硬件 Cache。虚拟地址转换物理地址时先查 TLB，命中就能直接得到物理地址，不必再访问内存中的页表，大幅加快地址转换；由于局部性的存在，TLB 的命中率通常很高。
标签：操作系统,内存管理
来源：个人笔记

## OS-020
题干：什么是缺页中断？它的处理流程是怎样的？
要点：程序访问的页不在物理内存时，硬件产生缺页中断，陷入内核处理。操作系统先判断访问是否合法，非法则报错终止；合法就从磁盘交换区把该页调入内存，有空闲物理页直接装入，没有就按页面置换算法淘汰一页再装入；随后更新页表映射，重新执行被中断的指令。缺页是换页机制的正常现象，频繁缺页才会拖慢性能。
标签：操作系统,内存管理
来源：个人笔记

## OS-021
题干：说一下什么是用户态和内核态？系统调用时发生了什么？
要点：内核是操作系统的核心，提供系统最核心的能力；用户空间的进程不能直接访问硬件和内核数据结构，只能通过系统调用请求内核服务。应用程序执行 open、read、fork 等系统调用时，CPU 从用户态切换到内核态，进入内核空间执行相应内核代码，完成后再切换回用户态返回结果。切换伴随 CPU 模式与上下文的改变，有一定开销。
标签：操作系统,系统基础
来源：个人笔记

## SP-008
题干：Spring 的单例 Bean 是线程安全的吗？怎么解决并发问题？

## SP-009
题干：说一下 JDK 动态代理和 CGLIB 动态代理的区别？

## SP-010

## SP-014
题干：说说 Spring 声明式事务的实现原理？

## SP-015
题干：说一下 Spring 事务失效的常见场景有哪些？
要点：一是方法内部 try-catch 把异常吞掉，事务通知感知不到，应在 catch 中重新抛出运行时异常；二是抛出检查异常，Spring 默认只回滚非检查异常，需配置 rollbackFor 属性指定回滚类型；三是方法不是 public，创建代理和事务增强都要求方法为 public；四是同类中方法自调用走的是原始对象而非代理，事务拦截不生效，需从外部调用或注入自身代理。

## SP-016
题干：说一下 Spring 的事务传播机制？
要点：传播机制定义一个事务方法被另一个事务方法调用时的事务行为。REQUIRED 是默认，有事务就加入、没有就新建；REQUIRES_NEW 总是新建事务并挂起当前事务；NESTED 开嵌套子事务，父事务回滚会带动子事务，子事务异常不一定影响父事务；SUPPORTS 有事务就加入、没有就以非事务方式执行；MANDATORY 要求必须存在事务否则抛异常。实现基于 ThreadLocal，跨线程调用时传播会失效。
标签：Spring,事务
